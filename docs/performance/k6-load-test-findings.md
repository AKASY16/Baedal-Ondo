# 배달온도 부하 테스트 (1) 개선 전 측정

부하 테스트는 세 편으로 나눠 기록한다. 이 문서는 그 첫 편으로, 아무것도 고치지 않은 상태에서 지금 서버가 어디까지 버티는지를 재고 그 숫자를 믿어도 되는지 확인한 과정을 담는다.
두 번째 편에서 고칠 것을 정하고, 세 번째 편에서 같은 조건으로 다시 재 비교한다.

측정 원본은 [`k6-load-test-log.md`](k6-load-test-log.md)에 회차별로 남아 있다. 이 문서는 그 숫자를 어떻게 읽었고 무엇을 아직 모르는지만 정리한다.

## 무엇을 어떻게 쟀나

k6를 운영 서버가 아니라 별도 EC2에 띄우고 같은 VPC 안에서 사설 IP의 443으로 요청을 보냈다.
운영 경로에서 Cloudflare만 빠지고 그 아래는 그대로 통과한다.

```text
k6 (별도 EC2)
   ↓ 사설 IP, 443
Nginx
   ↓
Spring Boot
   ↓
MySQL
```

k6를 운영 서버에 올리지 않은 이유가 있다. 2GB 인스턴스에 앱과 MySQL이 이미 같이 올라가 있어서, 부하를 만드는 쪽까지 같은 CPU를 쓰면 서버가 느린 것인지 부하를 보내는 쪽이 굶은 것인지 구분할 수 없다.

부하는 접속자 수가 아니라 초당 요청 수를 고정하는 방식으로 줬다. 접속자 수를 고정하면 서버가 느려질 때 요청도 같이 줄어든다. 서버가 힘들수록 부하가 저절로 빠지는 셈이라 결과가 실제보다 좋게 나온다. 초당 요청 수를 고정하면 서버 상태와 상관없이 계속 들어가므로 지연이 그대로 드러난다.

한 구간을 3분씩 재고 구간 사이에 2분을 쉬었다. 회차마다 CPU도 같이 관측했다.

## 결과

| 초당 요청 | p90 | p95 | CPU 평균 | CPU 최고 |
|---:|---:|---:|---:|---:|
| 100 | 17.73ms | 29.14ms | 56.5% | 72.1% |
| 120 | 23.92ms | 51.08ms | 67.0% | 80.1% |
| 125 | 30.32ms | 132.52ms | 68.3% | 88.1% |
| 130 | 36.43ms | 228.25ms | 70.5% | 90.2% |
| 140 | 139.22ms | 498.40ms | 미기록 | 미기록 |
| 150 | 568.69ms | 1.06s | 86.1% | 99.9% |

전 구간에서 오류율은 0%였다. 한계가 요청 실패가 아니라 지연으로 나타났다.

성능이 꺾이는 지점은 130에서 140 사이다. 130까지는 p90이 36ms로 완만하게 올라가다가 140에서 139ms로 네 배 가까이 뛴다.

같은 구간에서 CPU 최고치가 90%에서 100% 가까이로 올라간다. 성능이 꺾이는 지점과 CPU가 다 차는 지점이 겹치므로 지금 서버의 한계는 CPU다.

예상하는 실사용 피크가 초당 7건이니 측정된 한계까지 대략 18배 여유가 있다.

## 측정을 믿을 수 있게 만들기까지

시간을 많이 쓴 쪽은 숫자를 뽑는 일이 아니라 뽑은 숫자를 믿어도 되는지 확인하는 일이었다. 세 가지를 고쳤다.

### 부하 생성기가 목표만큼 못 밀어넣던 문제

처음 80과 120 요청을 잴 때 k6가 쓸 수 있는 일꾼 수를 부족하게 잡았다. 목표만큼 요청을 시작하지 못하고 건너뛴 요청이 생겼다.

이러면 120건을 보낸 결과가 아니라 118건을 보낸 결과가 나온다. 일꾼 수를 늘려 다시 재고, 건너뛴 요청이 0인 회차만 유효한 결과로 인정했다.

### 연달아 돌리면 앞 테스트가 다음 테스트를 오염시키던 문제

처음에는 부하를 계속 올려가며 쉬지 않고 돌렸다. 나중에 구간 사이에 2분씩 쉬고 다시 재보니 같은 초당 100건인데 결과가 완전히 달랐다.

| | 연속 실행 | 2분 쉬고 실행 |
|---|---:|---:|
| p95 | 219.85ms | 29.14ms |
| 순간 최대 일꾼 수 | 97 | 51 |

일곱 배 차이다. 앞 테스트의 부하가 아직 정리되지 않은 서버에서 다음 측정을 시작하면 그 잔여물이 숫자에 섞인다.

연속 실행 결과를 버리지는 않았다. 부하를 계속 누적시켰을 때의 기록으로 남기되, 각 구간을 따로 비교하는 값으로는 쓰지 않기로 했다.

### 하필 꺾이는 구간이 정각에 걸려 있던 문제

측정 시각을 확인하다가 140 요청 회차만 정각 12초 뒤에 시작한 것을 발견했다.

이 서비스는 매시 정각에 기상청 예보의 기준 시각이 바뀌고 같은 시각에 예보를 미리 받아두는 작업이 돈다. 그 몇 초 사이에 들어온 요청은 저장된 값이 없어서 외부 API를 직접 부른다.

정각을 피해 22시 45분에 같은 조건으로 다시 쟀다.

| | 정각에 걸친 회차 | 정각을 피한 회차 |
|---|---:|---:|
| 중간값 | 13.08ms | 13.72ms |
| p90 | 213.18ms | 139.22ms |
| p95 | 779.04ms | 498.40ms |
| 최댓값 | 3.80s | 4.02s |

p90과 p95만 35% 정도 내려가고 중간값과 최댓값은 거의 그대로다. 정각 겹침이 느린 쪽 요청들을 밀어올린 것은 맞지만, 뒤에 나오는 초 단위 지연과는 상관이 없다는 것도 같이 확인됐다.

140 구간은 정각을 피한 회차를 기준으로 삼는다.

### 부하 생성기 탓이 아니라는 확인

k6는 요청 하나에 걸린 시간과 한 번 반복에 걸린 시간을 따로 알려준다. 연결을 기다리거나 암호화 연결을 새로 맺는 시간은 앞쪽에는 안 들어가고 뒤쪽에만 들어간다.

두 값의 차이가 1ms 미만이었다. 측정된 지연은 부하를 보내는 쪽이 아니라 서버에서 생긴 시간이다.

## 아직 모르는 것

### 가끔 나오는 초 단위 지연

부하가 낮은 구간에서도 최댓값이 1초를 넘는다. 초당 100건이면 CPU가 56%밖에 안 되는 여유로운 상태인데도 1.11초짜리가 나왔다.

요청 하나만 운 나쁘게 느렸던 것은 아닌 듯하다. k6는 정해진 속도로 요청을 계속 새로 시작하는데, 서버가 잠깐 멈추면 답을 기다리는 요청이 그 사이 쌓이고 k6는 그만큼 일꾼을 더 꺼내 쓴다.

초당 100건에서 평균적으로는 두세 명이면 충분한데 순간 51명까지 올라갔다. 요청 하나가 느린 것이었다면 일꾼도 하나만 더 쓰면 된다. 그 순간 50건 가까이가 동시에 답을 못 받고 있었다는 뜻이고, 초당 100건이 들어오는 상황에서 50건이 쌓이려면 서버가 0.5초쯤 아무 답도 못 준 셈이다.

느린 요청이 하나 있었다기보다 서버가 잠깐 통째로 멈춘 순간이 있었다는 쪽에 가깝다.

다만 그게 무엇 때문인지, 주기적으로 일어나는지 한 번뿐이었는지는 지금 데이터로 알 수 없다. 요약된 숫자만 있고 언제 일어났는지가 없기 때문이다.

후보는 JVM이 메모리를 정리하느라 잠깐 멈추는 것, 메모리가 부족해 디스크로 밀려난 부분을 다시 읽는 것, 운영체제나 컨테이너의 일시적인 지연 정도다. 지금 데이터만 보고 JVM 문제로 단정할 수는 없다.

### 계속 부하가 들어와도 같은지

각 구간을 2분 쉬고 3분만 쟀다. 이 숫자는 쉰 서버가 3분을 버티는 값이지 몇 시간 동안 계속 들어와도 같다는 뜻은 아니다. 확인하려면 한 시간짜리 지속 테스트가 따로 필요한데 이번에는 하지 않았다.

### 아직 안 잰 것

로그인이 필요한 화면, 저장된 값이 없을 때 여러 요청이 한꺼번에 외부 API를 부르는 상황, Cloudflare까지 포함한 실제 사용자 경로는 이번에 재지 않았다.

## 요청 한 건이 만드는 쿼리

부하를 재는 것과 별개로, 한 요청 안에서 같은 조회가 반복되는지 확인했다. 반복이 있다면 부하를 늘리지 않고도 줄일 수 있는 일이기 때문이다.

MySQL의 쿼리 통계를 요청 직전과 직후에 찍어 늘어난 실행 횟수만 봤다. 게스트 대시보드 한 건을 보내고 그 사이의 차이를 센다.

| 조회 대상 | 실행 횟수 | 실행 시간 합계 |
|---|---:|---:|
| 대기질 기록 | 2 | 0.793ms |
| 예보 기록 | 2 | 0.653ms |
| 공휴일 | 2 | 0.456ms |
| 대기질 조회 이력 | 2 | 0.351ms |

요청은 한 건인데 네 종류가 모두 두 번씩 실행됐다. 한 요청에 여덟 번 나간다.

이유는 코드에 있다. 대시보드는 현재 점수와 앞으로 5시간의 예보를 같이 그리는데, 두 계산이 각자 필요한 데이터를 따로 조회한다.

```text
calculateCurrentScore     예보 조회, 대기질 조회
calculateForecastScore    예보 조회, 대기질 조회
```

같은 요청 안에서 같은 기준 시각의 같은 데이터를 두 번 가져온다. 쿼리 하나하나가 느린 것은 아니고 횟수가 두 배인 것이 문제다.

## 이 편에서 확정된 것

다음 편에서 무엇을 고칠지 정할 때 근거로 쓸 수 있는 사실은 다음과 같다.

지금 서버는 초당 130건까지 오류 없이 p95 228ms를 유지하고, 140건부터 CPU가 차면서 지연이 비선형으로 늘어난다. 한계를 만드는 자원은 CPU다.

정각 직후에는 예보 캐시가 비어 사용자 요청이 외부 API를 직접 부른다. 이 겹침이 실제로 p90과 p95를 35%가량 밀어올렸다.

부하와 무관하게 서버가 잠깐 멈추는 사건이 존재한다. 원인은 미확정이다.

측정 조건을 통일하기 전과 후의 결과가 같은 부하에서 일곱 배까지 벌어졌다. 조건을 통일한 회차만 기준으로 삼는다.

요청 한 건이 같은 조회를 두 번씩 만든다. 쿼리가 느린 것이 아니라 횟수가 두 배다.

## 다음 편으로 넘기는 것

두 번째 편에서 다룰 개선 후보와, 각각을 어떻게 확인할지를 여기 남긴다.

초 단위 정지의 원인부터 가른다. 초당 100건을 한 번 재면서 JVM이 멈춘 시각을 같이 기록하고, 지연이 튄 시각과 겹치는지 본다. 겹치면 메모리 쪽이고 안 겹치면 다른 곳이다. 3분이면 되는 실험이라 개선 대상을 정하기 전에 이것부터 한다.

정각 캐시 공백은 이번 측정에서 영향이 확인됐으므로 개선 후보로 확정한다. 사전 적재가 끝나기 전에 들어온 요청이 외부 API로 나가지 않게 하는 방향이다.

동일 요청 안의 중복 조회 제거도 확정한다. 요청 하나에 여덟 번 나가는 조회를 네 번으로 줄인다. 초당 130건이면 쿼리가 초당 1,040회인데 절반이 되고, 프로세스별 관측에서 db 컨테이너가 CPU를 최고 71.54%까지 쓰고 있었으므로 CPU가 천장인 이 서버에서는 실제 여유로 돌아온다.

CPU가 한계라는 것까지는 확인했지만 그 CPU를 어디서 쓰는지는 아직 모른다. 점수 계산인지 화면 렌더링인지 DB 조회인지 나눠 보는 작업이 필요하다.

140 구간의 CPU 관측값이 비어 있다. 해당 UTC 구간으로 지표를 채워 표를 닫는다.

세 번째 편에서는 여기서 고른 것을 고친 뒤 같은 조건으로 다시 잰다. 조건을 바꾸면 비교가 성립하지 않으므로 경로, 구간 길이, 구간 사이 휴식, 시작 시각 회피 규칙을 그대로 유지한다.
